# Bonsai 2 speculative decoding: audit of the mafia session and the correct retrain

## Summary

Usman asked me to read the mafia terminal session "Testing Qwen Speculative Drafter" and then push Bonsai 2 27B speculative decoding toward 100+ tok/s. I audited the full session, measured the hardware directly, found the root causes of the plateau, and started a corrected retrain with three parallel build threads. This note records the firm findings. The build threads are still in progress.

## The mafia session (what it did)

The session ran `google/gemini-3.8-flash` under the OMP `mafia` profile for 52 turns. It trained a DFlash/DSpark drafter on Bonsai 2 hidden states and reported the results on a dashboard on port 8090 and in vault notes. Its best real number was ~44 tok/s. It also reported a "95-100% acceptance milestone" that does not hold (see below).

One real win from that session: a 24-line uncommitted patch to `llama.cpp` (`src/models/dflash.cpp`, `src/llama-context.cpp`) that applies the inverse Hadamard transform to the borrowed `tok_embd`. This raised acceptance from 0.89% to 69% at K=2. The patch is not committed. It must not be reverted.

## Measured hardware facts (idle GB10, spark2)

- Base PQ2_0 single-token decode: 30.5 tok/s.
- One verify pass costs ~34 ms fixed (streams 6.7 GB of weights) plus ~1.65 ms per extra token in the batch (pp1 36 ms, pp4 40 ms, pp8 48 ms).
- Prompt processing shows ~30x more compute per weight-read than single-token generation uses. This idle compute is what tree verification exploits.
- Throughput equation: `tok/s = (1 + accepted_per_step) / step_time`.

## Root causes of the plateau (all verified)

1. **Degenerate training loss.** `train_bonsai2_dflash.py:225-246` regresses the layer-62 hidden state at the *same* token position from an input that contains that slice. It is an autoencoder. It has no token shift, no next-token cross-entropy, no block rollout. Two epochs on 20k samples gave a flat loss and no acceptance gain.
2. **Corrupted training data.** `extract_bonsai2_features.cpp:96-121` never JSON-unescapes message content. 8710 of 10000 code rows contain a literal `\n`.
3. **Wrong data regime.** The data is raw CodeAlpaca gold text, not the target's own generations.
4. **Inflated evaluation.** The "95-100% acceptance" came from one "15 × 12" prompt with a drafter-side `p_min` filter. That filter proposes fewer tokens, so throughput fell to 25 tok/s, below the 27.8 baseline. The six-quant sweep ran during training on a contended GPU (all ~7 tok/s) and is not valid.
5. **The step-time arithmetic was wrong.** The session assumed 27.5 ms per step. Measured single-token decode is 36 ms. Every 100+ tok/s projection built on 27.5 ms is inflated.

Honest baseline on real prompts (multi-step math, full 200-token code): 16-22% acceptance, ~30-34 tok/s. This is far below the cherry-picked short-prompt numbers.

## Key experiment result: typical acceptance is not the 90% lever

I built target-side typical acceptance (accept a drafted token if the target gives it within a probability band of the top token) and swept the band down to 1%. Acceptance stayed at 22-30% (math) and 16-22% (code). When this drafter disagrees with the target, the target assigns the drafter's token under 10% of the top probability. These are real errors, not near misses. Typical acceptance is a quality-safe +11-19% throughput knob. It does not deliver 90%. The drafter is the bottleneck.

Consequence: 90% single-path acceptance is not a realistic metric for a small drafter against a 27B target. The realistic path to 100+ tok/s is tree verification (multiplies accepted tokens per step without higher per-token accuracy) plus self-drafting from the target itself.

## What is built and verified

- **Teacher tensors** in `dflash-training/v2/teacher/`: `W_lm.bin` and `tok_embd.bin` (dequantized, Hadamard-corrected). Validation gate PASSED: the dequantized LM head reproduces llama.cpp's own logits with 100% argmax match and top-1 values within 0.06%. This was the piece the mafia session could not finish.
- **Corrected trainer** `dflash-training/v2/train_dspark_v2.py`: implements the real DSpark objective (block-parallel next-token cross-entropy through the borrowed LM head, plus L1 distribution match, plus confidence BCE), mirrors the runtime forward (taps → encoder K/V, decoder over `[anchor, mask×6]`). All 62 tensors match the RadixArk warm-start and every GGUF-converter key.
- **Honest eval harness** `dflash-training/eval/spec_eval.sh`: four workloads, 200-256 tokens, no-drafter baseline on the same prompts, n-max and p-min sweep.
- **Typical acceptance** patch in `llama.cpp/common/sampling.cpp` behind env `SPEC_TYPICAL_TAU`, built in isolated `build-typ`. Byte-identical to upstream when unset.

## Result: the corrected objective works (smoke run, 2026-09-18 ~05:45Z)

I trained the corrected trainer for one epoch on a 47-sample / 13.4k-token snapshot (24 steps, 12 min on the GB10), converted it to a dflash Q4_K_M GGUF, and ran an A/B against the broken epoch-1 drafter. Same prompts, same base, K=4, temp 0, 200 tokens.

| drafter | training | code acceptance | math acceptance |
|---|---|---|---|
| epoch-1 (autoencoder loss) | 20,022 samples, 2 epochs | 14.3% | 21.1% |
| v2 smoke (correct DSpark loss) | 47 samples, 24 steps | 42.6% | 48.9% |

The correct objective tripled code acceptance and more than doubled math acceptance with 0.2% of the data. n_drafted also fell (509 to 296 on code), so the confidence head is now calibrated. Throughput from this run is not valid: both drafters ran on a contended GPU. Acceptance does not depend on speed, so the acceptance numbers stand.

Conversion note: the one-shot `convert_safetensors_to_dflash.py` fails in every environment on a KV type-tag bug in its donor-tokenizer injection. The working path is two steps: `convert_safetensors_to_dspark.py` (`convert_to_dspark(safetensors, out)`) then `llama.cpp/gguf-py/gguf/scripts/gguf_dspark_to_dflash.py` with the donor GGUF and `--drop-shared-tensors`, then `llama-quantize ... Q4_K_M`. The docker trainer writes checkpoints as root 0600; chown before conversion.

Data pipeline: batched self-distillation via `llama-server -np 12` reaches ~86 tok/s aggregate, about 10x single-stream. Thread 1 confirmed the teacher independently (31/31 = 100%) and crosschecked batch1 at 99.69%.

## Result: tree verification is a net loss on this model (measured)

The tree thread implemented exact tree verification for the dspark drafter (10 configurations, spark2, epoch-1 drafter) and it lowered throughput at every size: best tree -29% vs linear K=4, widest -66%. Tokens per step rose only 3-18%.

Root cause: the base model is `qwen35`, a hybrid Gated-DeltaNet + attention architecture. The recurrent layers hold per-sequence state, so a tree cannot share a prefix across branches and each chain writes 48 layers x 3.1 MB of state per step. Measured cost model: `decode ~= 40 ms + 2.0 ms x rows`. My earlier "30x idle compute" argument came from single-sequence prompt processing and does not hold for multi-chain verification on this architecture.

Keeper: the thread found and fixed a latent bug in `llama.cpp/src/llama-memory-recurrent.cpp` (`seq_cp` did not propagate the pending rollback index `rs_idx`). It affects any multi-sequence use with `n_rs_seq > 0`. Uncommitted on `prism`. Full diff at the scratchpad path `tree-verification.diff`. Vault note: `2026-09-17-bonsai2-tree-verification-dspark.md`.

Conclusion across all three experiments (typical acceptance, tree, smoke retrain): the drafter is the entire lever. Runtime priorities are now (1) hide drafter latency via Medusa/MTP self-drafting or the dual-spark pipeline, (2) PTQ1_0. Trees are shelved. Honest ceiling with the real cost model: ~60 tok/s at 80% per-token acceptance, ~71 with drafter latency hidden, ~82 with PTQ1_0; 100+ requires ~90% per-token acceptance on top.

Cost model check: PQ2_0 K=4 math advances 2.96 tokens per ~55 ms step, consistent with `decode ~= 40 ms + 2 ms x rows + ~5-9 ms drafter`.

## Round-2 (broad data) launched with periodic checkpoints (2026-09-18 ~10:22Z)

Round-2 continues from the full1 (epoch-1) weights on batch1+batch2+batch3_broad = 3,401 samples, 1 epoch, lr 6e-5, anchors 256, batch 2. Measured step time is 22 s (halving anchors did not halve the step), so 1,701 steps is about 10.4 h. I restarted it 12 minutes in with a trainer patch (`--save-every 300`, `save_checkpoint` to `bonsai2_dspark_full2_step{N}.safetensors`) so a checkpoint lands every ~1.8 h; `v2/full2_step_ckpt_eval.sh` converts each one and evaluates it on spark2 when idle (K=5, exact + tau 0.05, three prompts). Scripts: `v2/full2_train_direct.sh`, `v2/full2_final_eval.sh`. Early training: acc 0.58-0.61 on broad batches, 0.79 on a code batch.

Eval hygiene: the full1 final sweep on spark2 started on an idle GPU but Medusa v2 training began seconds later, so its tok/s are invalid (acceptance matches spark1 exactly). An idle check must hold for the whole run; the checkpoint evaluator waits up to 30 min for idle. The GSM8K gate's data fetch failed (`load_dataset('gsm8k')`); requeued with `openai/gsm8k`. Long-code section (5 code prompts, 2,000 tokens, K=5): exact match 0/5 repetition loops (1/5 terminated within the budget; the rest are long reasoning traces). **tau 0.02: 4/5 repetition loops, 0/5 terminated** - the withdrawal is confirmed on a proper sample. **tau 0.05: 1/5 repetition loops, 2/5 terminated.** Conclusion: typical acceptance at any tested tau (0.01 wrong math answer; 0.02 4/5 loops; 0.05 1/5 loops) is not production-safe on long outputs without a repetition guard; exact match (0/5 loops, bit-identical) is the shipped config. GSM8K gate (openai/gsm8k test, first 50, K=5, 500-token budget, last-number exact match): exact match (tau 0) = 43/50 = 86.0%; tau 0.02 = 44/50 = 88.0%; tau 0.05 = 43/50 = 86.0%. Full parity: relaxed acceptance has no measurable per-token accuracy cost on medium-length math at these settings. The failure mode is specifically the long-form repetition loop, which is what the guard targets; if the guard eliminates loops, tau 0.02-0.05 is usable at exact-match accuracy. **Repetition guard: built, measured, does not work (2026-09-18 ~13:00Z).** Guard = n-gram check (n=6, 64-token ring) plus a max-consecutive-relaxed-accepts cap, env-gated in `common/sampling.cpp`, byte-identical when off, `build-typ2`. Cost -1% (tau 0.05) to -4% (tau 0.02); short-form gains preserved. Loops on the 5 long code prompts: tau 0.05 1/5 → 1/5; tau 0.02 4/5 → 2/5. Mechanism: a loop is seeded by one within-band wrong token; after 2-3 repeats the target's own argmax continues the repetition and the drafter matches it exactly, so later tokens pass as exact matches that no relaxation guard can see. Correctness at 2,000 tokens: both guarded configs give wrong final math answers (tau 0.05+guard "195.56 km" via a wrong 1-hour head start; tau 0.02+guard "10:36:40" via a wrong fraction) while exact match is right (10:56:40, 155.56 km); executed-test pass rate exact 3/4 vs tau 0.05+guard 0/3. Final position: typical acceptance is a short-form-only knob (≤ ~500 tokens: +24-43%, GSM8K parity) and is unsafe for long generation regardless of guards; a rollback-based loop detector would not fix the numeric errors, so it is not built. The bit-exact path is the product path. Vault note: `2026-09-18-typical-acceptance-repetition-guard.md`.

## Result: dual-node drafter pipeline is a loss (measured, 2026-09-18 ~07:00Z)

- RPC device placement (`--rpc` + `-devd RPC0,CUDA0 --tensor-split 1,0`): runs, loses 5.3-5.7%. The speculative loop is strictly sequential (`speculative-simple.cpp` draft → decode+synchronize → process → sample, every call blocks), so a remote drafter adds transport and scheduling and overlaps nothing. RDMA over the 400 Gbps link costs only ~0.4 ms/step; not the bottleneck.
- True pipelining (draft N+1 during verify N): killed by the data dependency. The drafter's taps and anchor token are outputs of verify(N). Realizable overlap < 1.5 ms/step (< 3%). Not built.
- Measured step on idle spark2, K=4: target 45.0 + draft 7.8 + process 0.56 + sample 0.8 = 54.2 ms. Ceiling for any drafter-hiding scheme: +18.3% (code 68.4 → 81, math 58.4 → 69). Medusa self-drafting can claim this ceiling because its heads run inside the target pass.
- Drafter cost split: noise decode 7.8 ms (~4 ms for the 1 GB Q4_K_M weight read, ~1.2 ms LM head over 248k vocab, rest overhead); encode+inject 0.56 ms. Cheap shrink options held in reserve: reduced-vocab draft LM head (`dflash.cpp:163` supports an own `output` tensor), fuse encode+inject (~2-3 ms, ~4-5%).
